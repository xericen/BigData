# Support 임계값에 따른 폭발 측정

## 측정 결과

20,000개 basket과 2,000개 item으로 생성된 고정 데이터에서 `PlainApriori`를
측정했다. 메모리는 Python `tracemalloc`의 peak 값이다.

| support | frequent pairs | peak counters | 시간 (초) | peak 메모리 (MB) |
|---:|---:|---:|---:|---:|
| 400 | 249 | 10,585 | 1.28 | 1.1 |
| 200 | 776 | 58,626 | 2.14 | 6.4 |
| 100 | 2,244 | 273,701 | 4.07 | 26.4 |
| 50 | 6,397 | 820,259 | 7.08 | 102.2 |
| 25 | 17,045 | 893,456 | 8.39 | 102.2 |
| 12 | 43,116 | 893,456 | 8.20 | 102.8 |
| 6 | 101,938 | 893,456 | 7.59 | 119.4 |
| 3 | 250,054 | 893,456 | 9.57 | 156.6 |
| 1 | 893,456 | 893,456 | 10.60 | 327.1 |

## 경계와 증가 형태

support를 400→200→100→50으로 반씩 낮출 때 counter 수는 각각 약
5.54배, 4.67배, 3.00배로 증가해 선형보다 훨씬 가팔랐다. support 25에서
관측 가능한 893,456개 pair counter에 거의 도달한 뒤에는 포화되었다.

이 컴퓨터에서는 실행이 실패하거나 RAM이 고갈되지는 않았다. 다만 support 1은
10.60초와 peak 327.1MB가 필요했고, 가능한 모든 관측 pair가 답이 되어 더 낮은
유효 임계값도 없으므로 여기서 중단했다. 먼저 부담이 된 자원은 메모리였으며,
counter가 아니라 반환할 답의 수가 마지막 메모리 증가를 만들었다.

## Counter와 답의 차이

support 50에서는 답이 6,397개뿐인데 이를 찾기 위해 820,259개 counter를
유지했다(약 128배). 임계값을 반으로 줄일 때 답은 대체로 2.4~3.1배 늘었지만,
초기 counter는 최대 5.5배 늘었다. 즉 조금 더 낮은 support를 요청해도 정답보다
후보 저장 공간이 먼저 폭발하며, 이 간격이 PCY 같은 사전 필터가 필요한 이유다.

## 실행 환경

- Windows 10 10.0.19045, Python 3.13.1
- Intel Core i7-7700HQ 2.80 GHz, RAM 17,024,520,192 bytes (약 15.9 GiB)
- Visual Studio Code, Chrome, Windows Defender, Codex가 함께 실행 중이었음
